**Word-to-PDF implementation and verification — October 23, 2026.**

The browser prototype now calls a real, local LibreOffice WebAssembly renderer from its normal conversion button. Five authored DOCX documents were converted through the UI, downloaded, independently reopened and rendered against Microsoft Word exports. A second production conversion succeeded with Chromium networking disabled. **Native Android does not yet contain an embedded DOCX layout engine. This is a verified web improvement and an honest Android limitation, not a declaration that the full product objective is fixed.**

The optional runtime is installed in this workspace for evaluation. Its approximately 250 MiB of generated assets are excluded from Git, are not downloaded automatically by npm install/build, and are not a license-complete redistributable FileFlow release. No paid dependency, cloud API, deployment, Supabase requirement or mandatory conversion backend was added. No personal document was used in this new suite or uploaded anywhere.

**Why the previous conversion failed.**

The previous browser button selected `docxToPdfLocal` in `web/src/lib/localWordPdf.ts`. It unzipped `word/document.xml`, collected paragraph text, and called jsPDF with fixed Helvetica 11, A4 dimensions, a 487-point text width, and newly calculated line wrapping. It never resolved Word styles, themes, font metrics, section dimensions, paragraph spacing/alignment, columns, numbering, positioned shapes, or document pagination. It rejected many tables/images/headers rather than render them. A styled CV and a multicolumn document still passed its narrow object checks and lost their design. This was text reflow, not a defective full office renderer that could be corrected by adjusting a few coordinates.

The native basic mode used `LocalDocumentProcessor.docxToPdf`, ZIP/XML text extraction, Android `TextPaint`/`StaticLayout`, and `PdfDocument`. It used fixed 595×842 pages and a single text layout. It did not interpret original DOCX layout either. Android's default office-app option opened the original URI with ACTION_VIEW; it was already connected to the UI, but it was a handoff, not an embedded conversion or a FileFlow download. The optional Java service used real desktop LibreOffice and remained a separately selected upload path.

**Current operation, from selection to saving.**

Browser: the dropzone selects the original DOCX → `DocumentConverter` defaults to `renderDocxOffline` → a same-origin manifest confirms that the optional engine is installed → the original bytes and optional font files are transferred into a short-lived rendering frame → LibreOffice loads the DOCX read-only and uses `writer_pdf_Export` → PDF bytes return through a checked same-origin message → pdf-lib independently parses the result and checks its page count → the existing result card saves a PDF through the browser. The document is never converted to an intermediate plain-text document or an HTML facsimile.

The frame uses the ZetaJS UNO API, `MacroExecMode.NEVER_EXECUTE` and `UpdateDocMode.NO_UPDATE`; its CSP limits network connections to its own origin. All engine code is served locally, not loaded from a vendor CDN during conversion. A three-minute rendering deadline, cancellation on screen removal, file/font limits, output validation and explicit error propagation prevent silent fallback. Missing engine, unsupported isolation, reported low memory, failure and malformed output produce an explanation without a successful result card. The service checkbox remains unchecked and mutually exclusive with plain-text export.

Original fonts matter. The renderer accepts optional local TTF/OTF files and registers them in the engine before it starts. The app does not read Windows fonts automatically or redistribute them. A font list is limited to 32 files, 10 MiB each and 40 MiB combined. Without the fonts, LibreOffice uses its bundled replacements, which can change typography and line wrapping substantially. Selected fonts remain local. Documents are limited to 20 MiB and returned PDFs to 100 MiB/100 pages.

The old exporter remains intact behind **Export basic text only (discard document layout)**. Its outputs are named `*-text-only.pdf` and its history entry says Word text export. It is never a fallback for office rendering.

Android: original URI selection and validation → an explicit spinner choice → installed-office ACTION_VIEW handoff, separate basic text export, or an explicitly configured service → existing SAF Save/Share for actual returned bytes. ACTION_VIEW has read-only URI permission and ClipData. A DOCX package-visibility query supports checking for a handler; missing apps and lost permissions now have clear errors. FileFlow does not claim an office-app export as its own output. `LocalDocumentProcessor.docxToPdf` now fails explicitly because there is no layout engine; only the distinctly named `exportDocxTextToPdf` can run the retained legacy exporter. Invalid engine indices fail rather than falling through to text export. Basic results/history are labeled as text-only with formatting discarded. English and Urdu explain the limitation.

**Original DOCX tests and measured results.**

The inputs were authored as DOCX, not reconstructed from PDF: a professional CV with centered Garamond heading, colored Arial section headings and paragraph spacing; a two-column Times New Roman newsletter with continuous sections; a two-page report with horizontal/vertical table merges, shading, a logo, headers/footers, numbering, hyperlink and explicit page break; Urdu/bidirectional and other Unicode text; and a colored positioned text-box shape. The user's earlier converted CV was not used as a quality benchmark in this new suite.

The reference is the installed Microsoft Word's native PDF export, performed with macro execution and link updates disabled. docx2pdf was separately exercised as a desktop benchmark. Comparisons render every page with PyMuPDF at 90 dpi, RGB, no alignment or resizing. Pixel error is mean absolute RGB difference on a 0–255 scale; foreground IoU uses an RGB-mean threshold of 220. Both measures are affected by font rasterization and small shifts; a reduction is **not** a percentage of conversion accuracy. PDF text is NFKC-normalized with whitespace removed, compared as sequence and character multiset. These small synthetic inputs are not a comprehensive DOCX corpus.

The “new” column below uses the actual web button with matching local source fonts selected. The no-extra-font result is also disclosed.

|---|---|---|

| Page count | CV 1 and newsletter 2, but original page size/layout lost; three other inputs rejected | All five match Word: CV 1, columns 2, report 2, Urdu 1, shapes 1; original Letter dimensions retained |

The report contains the same normalized character counts but PDF extraction order differs around table content. The CV, columns and shape sample preserve normalized text sequence. Urdu differs by one codepoint relative to Word extraction (U+06CC versus U+064A); its IoU is only .2645 and mixed-script spacing differs visibly. Unicode/RTL parity is **not solved**.

Without selecting the original fonts, the CV uses Noto Serif/Liberation Sans and its error is **13.2594**, worse than the previous export's 11.8733 despite retaining much more document structure. This is a verified limitation, not hidden behind the better font-assisted result. The actual default-button PDF is saved under `browser-after-default/`. Missing fonts cannot be recovered by changing text coordinates or silently downloading proprietary fonts.

**Verification and implementation limits.**

Web: 38 unit tests and type checking passed; production build passed; all 42 Playwright tests passed across desktop Chromium and Pixel 5 browser emulation. The Windows Playwright-owned Vite server needed explicit cleanup after all tests completed. The actual new conversion tests are separate from mocked/error-only regressions: five original DOCX files went through the real button and Save flow, their PDFs were reopened/rendered, and another five-conversion sequence checks engine teardown without reloading the screen. No document POST or outside-host request occurred. The production PWA passed both its Word conversion test with networking disabled and the existing offline PDF-to-Word/PDF-to-Excel test.

Memory follow-up found that simply removing the frame left worker targets alive. The renderer now owns Worker handles, terminates the Emscripten pool and auxiliary workers, and synchronously disposes before removing the frame. The repeated conversion check polls for worker teardown and verifies zero engine frames/workers. This is a bounded resource cleanup test, not proof of a full browser heap leak audit. Browsers reporting less than 4 GiB device RAM are rejected before initialization because this build reserves 1 GiB of linear memory.

Android: 21 JVM tests passed, including the guard that a document-conversion API cannot fall through to text reflow. Debug app and instrumentation APK builds and lint passed. The final resource change was rebuilt and linted. No Android device was connected; the SDK's emulator directory contained no runnable emulator. No native DOCX rendering, handoff UI, device font fidelity, speed or RAM result is claimed. The APK does not contain the browser runtime or a commercial trial SDK.

The exact native blocker is an absent, built-and-verified Android office core, not PDF writing. Android has no system DOCX layout API; `StaticLayout` cannot interpret Word sections, tables, drawings or pagination. A real LibreOfficeKit route needs ABI-specific `liblo-native-code.so`, its bootstrap/JNI interfaces, document filters, registry/assets/fonts, lifecycle/threading integration and license-complete distribution. Collabora's documented native build is a Linux engine build followed by the Android app build, not a Maven dependency. This machine does have Ubuntu WSL and GCC/G++, but lacks the required Linux make/autoconf/automake/pkg-config/clang/JDK toolchain and an Android native engine build/NDK setup; Docker's Linux daemon was unavailable. No prebuilt, verified SDK package was present. This is not a claim that an open-source native port is impossible: it remains an uncompleted substantial integration, and it cannot honestly be certified by this APK compiling.

The most realistic free offline Android path available now is the explicit office-app export handoff. Seamless conversion inside FileFlow requires building and integrating the actual LibreOfficeKit/Collabora core and validating it on Android; it does not require a paid API in principle. A licensed commercial Android renderer is another engineering route, but it is outside the requested no-paid-dependency constraint and was not added. The browser WASM experiment is useful for the prototype; its memory cost, WebView compatibility and unfinished distribution package make it an inappropriate shortcut into the production APK.

**Reproduce the locally verified web path.**

```powershell
# Explicit setup; no document uploads. Run once after reviewing the notices.
npm.cmd --prefix web run setup:office
# Or reuse this workspace's already-reviewed downloaded bytes:
node scripts/setup-office-runtime.mjs '--from-dir=.tools/word-pdf-rendering/research'
npm.cmd --prefix web run dev
```

Open Word to PDF, select an original DOCX, optionally select its matching local fonts, keep the text-export and upload choices unchecked, press Convert to PDF, then Save. A supported cross-origin-isolated browser is required; Vite/preview and the static hosting configuration include the required headers. Runtime files are cached locally after use rather than forcing every app installation to pre-cache hundreds of megabytes. A fresh checkout without setup gives the explicit missing-engine explanation. Setup is not a deployment step.
