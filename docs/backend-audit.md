# FileFlow backend repair notes — October 22, 2026

This document records source changes and the limits of their verification. It is not a production-readiness certificate. The server has no document database and guest processing remains available without Supabase login. Frontend authentication does not authorize or protect this API.

## API contract

`GET /api/v1/health/capabilities` returns HTTP 200 for a reachable service even when degraded. `status` is `ready` only when both office dependencies pass their startup probes; optional qpdf does not prevent Java compression. `operations` lists currently available operations. `dependencies` contains boolean `pdf-to-docx`, `docx-to-pdf`, and `qpdf` entries. `dependencyCheck` describes the probe and cache, so a successful probe is not confused with document-fidelity certification.

`POST /api/v1/pdf/tables/xlsx` remains compatible with existing review payloads. Omitted `columnTypes` preserves all values as text. If column types are supplied, the first row remains text and subsequent rows use those types. Invalid explicit conversions fail visibly instead of silently changing a value. Merged-cell structure, multi-page table joining, currency recognition, and locale/date inference are not reconstructed automatically.

## Verification and remaining boundaries

The tests under `server/src/test/java` run the real PDFBox, Tabula, POI and compressor implementations. API tests use Spring MockMvc with real services; missing-engine scenarios deliberately configure absent executables. They do not simulate successful Word conversions. `ProcessingQualityTest` opens produced PDFs and workbooks, checks selective text retention, and verifies the existing structured DOCX fixture. `ResourceSafetyTest` executes a real Java process to verify timeout cleanup. The main audit records final command results and live HTTP/engine checks.

The final Java suite contains 23 tests covering request admission, real PDF/table/workbook processing, API contracts and cleanup. `mvn package` succeeded after normal dependency retrieval populated uncached packaging plugins; the runnable artifact is `server/target/fileflow-processing-0.2.0.jar`. Intermediate failures are not counted as passes: four JUnit cleanup errors initially came from restricted access to the default Windows temp directory, and a later timeout test encountered a transient process working-directory lock. Surefire now sets the JVM temporary directory at process startup to the existing Maven target directory. The timeout test captures and checks the actual process even if it never reaches its main method, and its child uses a persistent working directory. Process cleanup now waits for attached descendants as well as the parent and reports failure if they remain alive.

Actual corrected CLI checks ran three generated fixtures through `python -m pdf2docx.main convert`: all 25 checked text fragments remained editable, the ruled table and embedded image were preserved, and checked bold/italic runs remained styled. Conversion subprocess times were 1.54, 1.67 and 1.75 seconds in that run. A footer was retained as ordinary text rather than a semantic Word footer. These are limited synthetic checks on this machine; see the main conversion-quality report for reproducible fixtures and remaining fidelity gaps. They are not general production performance or pixel-fidelity claims.

No paid API, OCR subscription, database, cloud host, or persistent document store was introduced. Actual backend hosting, HTTPS and a configured frontend base URL are still required; Vercel static frontend deployment does not run Spring Boot. Deploy the existing container or Java server with LibreOffice and the configured PDF-to-DOCX engine. See deployment documentation for proxy/body/time/memory limits and environment setup.

Public release still needs hard process/container isolation for hostile PDFs, egress restrictions for office engines, current dependency/security review, representative real conversion-quality comparisons, and concurrency/load/memory tests on the intended host. Java parsing/extraction uses cooperative page/resource deadlines, not a hard per-document CPU sandbox. Whole uploads and downloads are still buffered byte arrays; the admission and size limits bound requests but do not eliminate memory pressure. Rate limits are per server instance; distributed abuse protection belongs at the trusted reverse proxy. Detached child processes and operating-system cleanup failures cannot be ruled out by the attached-tree/workspace tests.

Scanned documents still require OCR, and a PDF-to-Word engine cannot guarantee original typography, arbitrary graphics, lists, merged tables, or pagination. Do not describe the current output as pixel-perfect. The existing PyMuPDF dependency also needs an open-source/commercial licensing decision before release; no paid license was purchased by these changes.
